# Spike: tmux control mode — results (2026-09-04)

- tmux version: 3.7c (`/opt/homebrew/bin/tmux`).
- GUI-attached session: created via `osascript -e 'tell application "Terminal" to do script "tmux -L sbspike new-session -s spike"'`. The Terminal automation Apple Event succeeded (after an initial attempt hit an AppleEvent timeout waiting on the macOS Automation permission prompt), but the session ended up hosted in an **iTerm2** window rather than a fresh Terminal.app window — `list-sessions`/`list-clients` confirmed a single `spike` session with one GUI client (`client_control_mode=0`) throughout both runs.
- **Final recorded run uses `-C attach-session -f ignore-size` (no `read-only`)** — this is a fixed-round-1 design ruling (spec §8.11/§18.10 updated): control clients attach with `ignore-size` only, not `read-only`, so the client's own `send-keys` succeeds and real `%output` events land in the transcript. The script (`apps/agent/scripts/spike-tmux.ts`) was updated accordingly; see "Fix round 1" below.
- `-C attach -f ignore-size` resized the GUI session: **no**. `#{window_width}x#{window_height}` measured `80x24` before any control client attached, and `80x24` again while the control client was attached — verified across both the original spike run and the fix-round-1 re-run (measured externally, ~0.6s into `pnpm spike:tmux`, both times). Spec 18.10's polling-`capture-pane` fallback is **not needed** — `ignore-size` reliably prevents the resize.
- `%output` events arrived after send-keys: **yes**, in the final recorded run (`-f ignore-size`, no `read-only`). The script's own `send-keys -t %0 -l -- 'echo shellbell-tmux-spike-ok'` (and the following `Enter`) succeeded, and dozens of `EVENT %output %0 ...` lines streamed in real time — first character-by-character (from the literal `-l` send and its terminal echo), then the full escape-sequence redraw, ending with `shellbell-tmux-spike-ok` visibly printed in both the console log and the GUI pane (confirmed via `tmux capture-pane`).
  - **Why the design was changed to drop `read-only` (kept here as the reasoning record)**: the *original* run used `-f read-only,ignore-size` per the initial brief, and the script's own `send-keys` was rejected with `%error ... client is read-only`, producing no `%output`. Investigation showed this is not just "the read-only client can't send its own keys" — while *any* client is attached to the session with `-f read-only`, `send-keys` is rejected for *every* client, including a completely separate, freshly-invoked `tmux send-keys` process unrelated to the read-only client. Reproduced twice. The moment the read-only client detached, the identical out-of-band `send-keys` succeeded immediately. tmux's manpage states read-only "only affects keys bound to detach-client/switch-client" for that client specifically — the observed session-wide blocking of `send-keys` from unrelated invocations was stronger than documented, and made a read-only observer incompatible with using the same client for remote key injection. A read-only client was confirmed to still *receive* `%output` normally for activity from other sources (e.g. a background loop started before it attached) — it just can't be the transport for injecting keys itself. Given the controller's ruling that control clients use `ignore-size` only (no `read-only`), this spike's final recorded run and fixture reflect that.
- `list-clients` shows our client with `client_control_mode=1` and the GUI client with `0`: **yes**. `list-clients -F '#{client_session}\t#{client_control_mode}'` → `["spike\t0", "spike\t1"]`.
- `capture-pane -e` inside `%begin/%end`: ESC arrives as **literal byte** (0x1B), not the text `\033`. Confirmed by `JSON.stringify()` of a captured reply line showing `\u001b` (Node's own escaping of a real control byte), not a literal 3-character `\033` text sequence:
  ```
  "\u001b[38;5;31m\u001b[48;5;234m \u001b[1m\u001b[38;5;39m~\u001b[0m\u001b[38;5;31m\u001b[48;5;234m \u001b[39m\u001b[49m \u001b[32mprintf\u001b[39m \u001b[33m'\\e[1;31mred bold\\e[0m normal\\n'\u001b[39m                  \u001b[38;5;70m\u001b[48;5;234m ok \u001b[38;5;242m|\u001b[38;5;66m 02:43:51 PM \u001b[39m\u001b[49m "
  ```
  (Note the `\\e` inside the quoted `printf` argument text is the literal two characters `\` `e` typed by the user — genuinely different from the real \u001b ESC bytes surrounding it, which is exactly the distinction this spike needed to make.) Spec 8.11 unescape rule: **keep as-is** — no text-`\033`-to-byte unescaping is needed; the parser should consume the ESC byte (0x1B) directly from the control-mode stream.
- capture-pane reply latency: p50 = 0.0 ms, max = 0.1 ms (20 samples, local UNIX-domain-socket tmux server on the same machine — not representative of any real network/remote hop, only of protocol/IPC overhead; the first run measured p50=0.1/max=0.3 ms, both effectively "sub-millisecond local IPC").
- Transcript: `apps/agent/test/fixtures/tmux-transcript.txt` (reviewed for secrets: yes). The transcript is from the final, fixed-script recorded run and is **complete** — 610 lines, 29 balanced `%begin`/`%end` pairs, 0 `%error`, ends with a proper `%end` followed by `%exit` (no truncation, unlike the first run — see "Fix round 1" below for why the first run's transcript was cut off mid-block). One line (the shell's OSC 7 working-directory escape sequence) contained this machine's real hostname and home path (`file://Bilals-MBP/Users/bilal`); it was sanitized in place (letters→`x`, digits→`0`, protocol markers left intact) to `file://xxxxxx-xxx/xxxxx/xxxxx`. ## Fix round 1 (controller rulings applied)

1. **Lint**: byte-identity applies to protocol artifacts, not scripts. Ran `pnpm lint:fix` on `apps/agent/scripts/spike-tmux.ts` and kept the result (reformatted: multi-line call/import wrapping, merged the two `node:fs` imports). `pnpm lint` now passes with exit 0.
2. **Crash fix**: added `transcript.on("error", () => {})`; guarded every transcript write with `if (!transcript.writableEnded)`; moved the stream's `.end()` out of `main()` and into `rl.on("close", () => transcript.end(() => process.exit(0)))`, so it only closes after the control client's `%exit`/stdout-close has actually been observed, and `process.exit(0)` only fires once the stream has finished flushing. Re-run now exits 0 with no crash.
3. **Design ruling applied**: removed `read-only` from the client's `-f` spawn arg (now `-f ignore-size` only), so the script's own `send-keys` succeeds and the transcript records real `%output` events, matching the updated spec §8.11/§18.10.
4. Re-ran the full spike against a freshly reopened GUI-attached session (iTerm2, `spike`, 80x24) with the styled line re-injected. Confirmed: `EVENT %output` lines appear after send-keys, `shellbell-tmux-spike-ok` shows in the GUI pane, transcript ends with a full `%end` (not mid-block), size still 80x24 during the run, and `tmux -L sbspike kill-server` was run afterward.
